# 项目 SDD 开发流程

建立日期：2026-08-26。用户已要求整个开发流程采用 SDD（Spec-Driven Development，规格驱动开发）。

本项目采用「约束 → 需求规格 → 技术计划 → 任务 → 实现 → 验收」流程，参考 [GitHub Spec Kit](https://github.com/github/spec-kit)。这里只建立项目内文档与评审规则，**尚未安装或运行 Spec Kit CLI**，也不假定用户指定了某一种 SDD 工具。

## 1. 文档与约束

- [AGENTS.md](../AGENTS.md)：技术栈、安全边界、固定 16 只怪兽等强约束，不另建一份相互竞争的项目宪章。
- [Agent V0.4 基线](../doc/mood-monster-agent-v0.4-plan.md)：已有产品闭环与数据规则。
- [视觉基线](../doc/mood-monster-visual-design-guidelines-v0.1.md)：品牌、组件、导航与适配规则。
- 各功能目录的 `spec.md`：要解决的问题、范围、需求编号和成功标准。
- `plan.md`：实现选择、接口、数据流、安全和风险。
- `tasks.md`：实现顺序、依赖、责任与需求映射。
- `acceptance.md`：验收案例与实际证据，未运行必须标为未运行。

当前功能：[002 — 电脑端核心流程预览](002-desktop-preview/spec.md)，用户已确认范围，进入实施。 [001 — Web 朋友内测版](001-web-friends-beta/spec.md) 保留为后续云端交付草案，本轮不进行真实 API 接入或在线部署。

## 2. 阶段与门槛

| 阶段 | 产物与通过条件 |
|---|---|
| Specify | 区分用户已确认事实、默认假设与待决事项；每个 P0 需求可验收 |
| Review | 用户确认需求范围，记录确认日期与原话摘要；不得把助手的假设标为用户已确认 |
| Plan | 技术方案遵守已有约束；接口、异常、安全、外部依赖已明确；可先编制草案 |
| Tasks | 每项任务映射需求与验收案例；实现前检查三者一致性 |
| Implement | 按任务完成最小修改；优先运行已有测试，再为缺口补测试；保留他人的未提交修改 |
| Verify | 保存实际测试、浏览器、云端联调证据；未通过的 P0 不可勾选完成 |
| Release | 环境、预算、访问保护和回滚方案就绪；由用户批准对外部署及费用相关配置 |

新功能的需求范围未获确认前，可以读取、研究、起草方案和验证现有基线，不修改业务行为。需求确认后，按已批准范围持续实现，不要求用户逐个批准代码文件。

## 3. 变更与完成定义

1. 需求变化先修改规格，或与实现同批修改；同步技术计划、任务和受影响案例。
2. 影响范围、费用、隐私或安全边界的变化需再次确认；局部实现调整记录原因即可。
3. 测试记录包含日期、命令或操作、环境、结果、证据位置；不使用历史通过记录代替当前验证。
4. 「代码完成」「本地验证」「真实模型联调」「朋友可访问」分别记录，不能互相替代。
5. API Key 不写入规格、聊天示例、浏览器配置、版本库或测试证据；示例只用占位符。
6. 未经明确要求，不安装额外 SDD 工具，不启用 superpowers，不擅自使用多 Agent。
